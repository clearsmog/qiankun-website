# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase is ~90% deletion. It does not touch typography, colour tokens, or
the visual system — those belong to Phase 3 (token consolidation) and Phase 4 (Position &
Design). This contract covers exactly the three surfaces this phase's deletions leave
visually unresolved: the homepage features row, the `/blog/` → "Writing" index, and the
vacated space where "Recent Posts" used to sit. Everything else on the homepage (hero name,
tagline, CTA button text) is explicitly out of scope and must not be touched by the executor
under this spec.

## Surface 1 — Homepage Features Row

**Locked:** row keeps exactly three cards (PRUNE-05); the two removed cards ("Technology",
"Writing") are replaced, not left as a gap. Trio and copy are at Claude's discretion provided
every link resolves to a surviving page.

**Trio (replaces Technology/Writing, keeps Projects unchanged):**

| Position | Card | Icon | Link | Title | Details copy |
|----------|------|------|------|-------|---------------|
| 1 (unchanged) | Projects | existing chart/bars glyph, gradient id `proj-grad` | `/projects/` | `Projects` | *(unchanged — existing copy already fine)* "Case studies for hiring managers — portfolio construction, systematic alpha research, ESG, valuation, and data storytelling." |
| 2 (replaces "Technology") | About | person/profile outline glyph, gradient id `about-grad` | `/about` | `About` | "Background, experience, and how I approach quantitative problems." |
| 3 (replaces "Writing") | Contact | envelope/mail outline glyph, gradient id `contact-grad` | `/contact` | `Contact` | "The fastest way to reach me directly." |

Rationale for this trio: it is the "safe default" the context doc names explicitly — every
card resolves to a page a hiring manager actually needs (portfolio, credibility, a way to
reach out), and none references a page this phase deletes.

**Icon contract:** follow the existing pattern exactly — inline `<svg>` in YAML frontmatter,
`width="32" height="32" viewBox="0 0 24 24" fill="none" stroke="url(#{id}-grad)" stroke-width="2" stroke-linecap="round" stroke-linejoin="round"`, with a `<defs><linearGradient>` using
the same two stops as the existing cards (`#667eea` → `#ec4899`). **Each card's gradient `id`
must be unique** (`about-grad`, `contact-grad`) — reusing `tech-grad`/`write-grad` ids after
those cards are deleted is fine structurally, but do not reuse the *same id* across two cards
that render simultaneously (SVG `<defs>` ids are global to the rendered DOM). Use any
simple, recognisable Lucide/Feather-style outline shape for "person" and "envelope" — exact
path data is implementation detail, not a contract point; the stroke style and gradient
must match.

**Copy is provisional, not final:** Phase 4 (POS-*) rewrites all homepage prose, including
these three `details` strings, once the overall positioning narrative is set. This phase's
job is only to ensure no card is broken, missing, or points at a phantom page — not to
finalize voice. Do not treat the details copy above as precious; it exists so the build does
not ship with a placeholder or a dead link in the interim.

**Grid/responsive behaviour:** the card count stays at three (was three, is three — two
cards are *replaced* in place within the existing `features:` array, not added or removed
from it). VitePress's default `VPFeatures` component already lays out a 1/2/3-column
responsive grid with no custom grid CSS in this codebase — `custom.css` only overrides
padding at the existing 768px breakpoint (`custom.css:524-536`), not `grid-template-columns`.
**No grid CSS change is required or permitted in this phase.** If the executor finds
themselves writing new `grid-template-columns` rules to "fix" the features row, that is a
signal something in the `features:` array count is wrong (should still be exactly 3 entries).

## Surface 2 — `/blog/` presented as "Writing"

**This is the single most important contract in this phase.** URLs stay `/blog/`
(relabel-only, per locked decision) — only the nav label, sidebar label, page `<title>`,
H1, and body copy change.

**Nav (`docs/.vitepress/config.js:158`):** `{ text: "Blog", link: "/blog/" }` →
`{ text: "Writing", link: "/blog/" }`.

**Sidebar:** the `/blog/` sidebar section's `text:` field (currently "Blog" or similar,
wherever it renders as a group heading in the sidebar object) also becomes "Writing" for
label consistency with the nav — a visitor should never see "Blog" in one nav element and
"Writing" in another for the same section.

**Page content contract — exact replacement for `docs/blog/index.md`:**

The current page fails PRUNE-11 in three ways: (1) the H1 says "Blog", (2) the intro line
"Welcome to my blog! Here you'll find articles..." is generic filler that reads as
copy-paste boilerplate, and (3) the "## Recent Posts" heading plus a three-item bullet list
plus "*More posts coming soon...*" all actively signal "this is a stream, and it's stalled"
— exactly what a single surviving post must not look like.

The fix is structural, not decorative: **stop presenting the one post as a list item inside
a "recent" feed, and present it as a standalone, titled piece of writing.** No bullet
point, no "Recent Posts" heading, no plural "articles," no "coming soon."

```markdown
---
title: Writing
description: Notes on energy trading systems, from direct implementation experience.
---

# Writing

### [Energy Trading and Risk Management (ETRM) Systems](/blog/etrm-systems)

A comprehensive look at ETRM software, market trends, and implementation — drawn from
hands-on work building trading infrastructure.

*19 January 2026*
```

Contract details:
- Frontmatter `title` changes from `Blog` to `Writing` (drives `<title>` tag and OG title).
- Frontmatter `description` changes from the generic "Articles and thoughts on technology
  and development" to a line that actually describes the one surviving post's subject —
  do not leave a description promising breadth the page does not have.
- H1 is `# Writing`, matching the nav/sidebar label exactly.
- The post is rendered as an `### H3` link (title is the link, matching how a single
  "featured piece" reads, not a bare bullet), followed by its one-line description as a
  plain paragraph, followed by the date in italics (`*19 January 2026*` — the date already
  exists in `etrm-systems.md`'s frontmatter, `date: 2026-01-19`; format it as written above
  or any unambiguous day-month-year — exact date format is not a contract point, but a date
  must be present so the entry reads as dated, deliberate work rather than an anonymous stub).
- **No new CSS class.** The structure above renders entirely through existing global
  `vp-doc` styles (`h1`, `h3`, `p`, `em`) already defined in `custom.css`. Do not add a
  `.writing-entry`/`.featured-post` wrapper or any bespoke styling here — that is exactly
  the kind of visual-system decision Phase 4 owns, and one-off CSS added in Phase 2 would
  conflict with Phase 4's restyle.
- Do not add placeholder text implying more posts will appear ("more soon," "stay tuned,"
  etc.) — PRUNE-10 explicitly bans staleness language, and inventing a new instance of it
  while removing the old one defeats the requirement.

## Surface 3 — Vacated Space Where "Recent Posts" Was

**Locked:** the "Recent Posts" block (heading, `<script setup>` data import, markup, and its
entire `<style>` block) is deleted from `docs/index.md` outright — not replaced with a new
section.

**Contract: nothing new fills this space, and nothing needs to.** After deletion, the
homepage's structure is `VPHero` → `VPFeatures` (three cards) → `VPFooter`. This is the
same generic structure VitePress ships by default for a `layout: home` page, and it is not
"abrupt" — it is the standard, expected shape of a hero-plus-features landing page. Verify,
don't invent:

- `VPFeatures` already carries `padding: 64px 24px !important` (`40px 20px` at ≤768px,
  `custom.css:193` and `:529`), giving generous closing whitespace under the three cards
  before the footer begins. This is existing, unmodified CSS — no new spacer element,
  divider, or CTA band is needed or wanted here.
- `VPFooter` (configured in `config.js:225`) already renders `message`/`copyright` text
  sitewide via `.VPFooter .message, .VPFooter .copyright` (`custom.css:393-397`) — the page
  does not end on empty space, it ends on the same footer every other page on the site
  already ends on.
- **Do not add a new homepage section** (a "Latest Writing" teaser, a second CTA row, a
  testimonial strip, etc.) to fill the gap. That is scope creep into Phase 4's positioning
  work and directly contradicts this phase's "prune, don't add" mandate. If the page feels
  thin after this deletion, that is a Phase 4 concern to solve with copy and layout, not a
  Phase 2 one to solve by inventing a new component.
- Confirm after deletion: `docs/.vitepress/data/blog-posts.data.js` has no remaining
  consumer (it was only ever imported by the now-deleted `<script setup>` block in
  `docs/index.md`). If grep confirms zero remaining imports, delete the file — it is dead
  code, not a UI surface, but leaving it is an easy miss the checker should catch.
