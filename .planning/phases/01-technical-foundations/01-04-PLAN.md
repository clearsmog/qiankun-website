  <action>
    This is the thin end-to-end slice: content page -> component -> theme slot -> layout -> rendered HTML on a sidebar-bearing page. Build all three pieces and prove the whole path in one pass, because the only real risk here is the last hop.

    Create `docs/privacy.md` following the `contact.md` convention exactly. Frontmatter carries a `title` of Privacy and a short `description`. The body states that the site uses Cloudflare Web Analytics for aggregate traffic measurement, that it sets no cookies and stores no persistent identifiers, and that standard request metadata such as IP address and user agent is processed transiently to produce aggregate counts, as any analytics service must, with nothing retained that identifies a visitor individually. Wording is at your discretion, but stay inside that factual boundary: do NOT write that the site collects no personal data at all, because IP address is personal data under UK GDPR and is transiently processed — an overclaim on a public page is worse than a precise one. Close with an italicised last-updated line, matching the sign-off convention the other content pages use. Keep it short; this is a utility page, not an essay.

    Create `docs/.vitepress/theme/PrivacyFooterLink.vue` as a minimal slot-only component: a `<script setup>` block, a template containing a single wrapper element with an anchor pointing at `/privacy` labelled Privacy, and a `<style scoped>` block. Style it as a quiet, centred, small-text line with modest vertical padding, using the site's existing CSS custom-property tokens for colour rather than literal colour values, so it inherits dark mode automatically. Follow the project's Vue conventions: PascalCase filename, `<script setup>`, scoped styles, kebab-case class names, two-space indent, no semicolons.

    Wire it into `docs/.vitepress/theme/index.js`: add the import alongside the existing `JsonLd` and `NotFound` imports, and add a `'layout-bottom'` entry to the slot object already being passed to the default theme's Layout, using the same arrow-function-returning-`h(Component)` form as the two entries already there. Do NOT add it to the component registration list inside `enhanceApp` — that list is reserved for components invoked directly inside markdown, and the two existing slot-only components are correctly absent from it.

    Do NOT use `themeConfig.footer` for this link and do NOT modify the existing footer block in `docs/.vitepress/config.js`. VitePress's shipped footer component hides itself with a CSS rule whenever the page has a sidebar, which is every page under `/projects/` and `/blog/` — the majority of this site's substantive content. A link placed there would render on the homepage and vanish on the case studies, and a homepage-only check would pass while the requirement went unmet. The `layout-bottom` slot is emitted unconditionally by the layout, which is why it is the chosen route. Equally, do not add a CSS override forcing the shipped footer visible — that fights the theme instead of using its extension point.

    Then build and verify against the built HTML of a case-study page specifically. That assertion is the whole point of this task; a check that only looks at the homepage would pass while the bug survived.

    On sitemap and robots (left to discretion in the phase context): no change is needed to either. The sitemap is generated from the page set by the existing config block, so the new page is included automatically, and `docs/public/robots.txt` already allows all paths. Confirm both rather than assuming, and record the conclusion.
  </action>
