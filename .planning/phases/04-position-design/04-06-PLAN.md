<objective>
Make the ten chart components capable of everything the exhibit quality bar asks of them: labelled
axes with units, motion that respects the visitor's reduced-motion preference, only declared font
weights, and semantic colours resolved from tokens rather than hex literals.

Purpose: EXH-01 requires every exhibit to carry labelled axes including units, and only one of the
ten components can do that today. DES-09's canvas half cannot be satisfied by CSS at all — ECharts
renders to canvas and ignores media queries, so each component must gate its own animation in
JavaScript. All ten changes are mechanical and follow a single existing reference implementation.

Output: eight components gaining optional axis-title props, ten gaining reduced-motion gating, three
losing a non-standard weight, and the semantic colour path wired end to end.
</objective>

Extend each target component's per-item colour resolution so an item may name a semantic colour
instead of supplying a hex value. The resolution order is: if the item's colour value is the string
naming the negative semantic, use the negative token; if it names the positive semantic, use the
positive token; if it names the muted semantic, use the theme object's existing `text3` value, and if
it names the muted-strong semantic, use the existing `text2`; otherwise fall back to the item's own
value if present, and finally to the sequential palette entry for its index. Write this as one
consistent expression across all seven components so a reader recognises it immediately. Update each
component's item-shape doc comment above `defineProps` to record that the colour key now accepts a
semantic name as well as a raw value or nothing.

This extension exists so that case-study markdown can write a meaning rather than a hex. The negative
and positive slots are deliberately two named slots, not a general theming layer — the site has
exactly two *sentiment* colour needs. Do not add a third sentiment slot and do not derive these from
the sequential palette; the palette happens to contain a similar green, but the two are different
concepts and coupling them means a future palette edit silently changes what "positive" means.

The muted names are **not** new slots and add nothing to `themeTokens()` — they are read-only aliases
onto `text3` and `text2`, which already exist (`echarts-setup.js:71-72`) and already re-theme. They
are needed because roughly a dozen chart items across the five case studies use a neutral grey to
mark a series as *recessive* — a baseline, benchmark, or reference range that must stay visually
subordinate to the data plotted against it (`'Whole economy'` and `'Rest of UK finance'`, both
literally labelled `sub: 'baseline'`; the `'Market'` benchmark; Cisco's `'52-week range'`; the
BRAIN composite comparison). Those greys are `#86868b` and `#6e6e73`, which are exactly the
`--vp-c-text-3` and `--vp-c-text-2` values. Without a way to name them, plans 04-07 to 04-09 would
have to delete the key and let a benchmark take a saturated palette hue — making it read as a
competing data series, against DES-12 and EXH-05.

Then fix the two direct component-level literals in `EFootball`. Its market-price marker is not driven
by the item data — it comes from a separate prop — so it is not fixable from markdown. Both its label
background and its dashed line colour currently name a red hex directly; resolve both from the
negative token on the theme object instead. This marker is the pivot of the Cisco page's entire
valuation claim and is one of the elements that visibly fails to re-theme in dark mode today.

Also fix one adjacent hard-coded fallback while you are in the file: `ECombo`'s line-series fallback

  </action>
