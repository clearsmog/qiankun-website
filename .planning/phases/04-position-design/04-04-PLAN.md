Add two keys to the object `themeTokens()` returns, using the identical `cssVar(name, fallback)` call
shape every other key already uses: `negative` reading `--color-negative` with a literal fallback of
the same value declared in `custom.css`, and `positive` reading `--color-positive` likewise. Place
them after `bgSoft` and before `palette`. No new SSR-safety code is needed — the fallback argument to
`cssVar()` is the entire mechanism, and it is already proven for `brand` and the text tokens.

Do not derive these from the `palette` array and do not remove any entry from it. The array contains
a purple and a green as ordinary sequential-fallback colours; one of them happens to share a hex with
the positive semantic token. They are a different concept and must stay textually separate object
keys, or a future edit to the sequential palette will silently change what "positive" means.

Add one new named export, `prefersReducedMotion`, exactly as UI-SPEC's Motion Contract specifies: a
short function returning whether `window` exists and the reduced-motion media query matches. Guard
the `window` access so the function returns false during the build-time server render rather than
throwing. Follow this file's convention for helpers — small, pure, no doc comment beyond what the
name already says.

The honest limitation, worth a one-line comment in the file: this is read at option-evaluation time,
not live-reactive, so an OS-level preference change mid-session will not update a chart until its
next re-render. That is acceptable for entrance animations, which play once per mount; continuous CSS
transitions are covered live by the `reduce` media block added in plan 04-02.
  </action>
