# Phase 4 — UI Design Contract: Position & Design

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is the largest UI phase in the milestone — it rewrites positioning copy
and rebuilds the typographic/visual system across all ten remaining pages: homepage, About,
Contact, `/projects/` index, five case studies, `/blog/` (Writing). 04-CONTEXT.md's decisions
are authoritative and locked; this contract turns them into exact token values, exact copy,
and exact per-component fixes so the planner can decompose into buildable plans without
re-deciding anything CONTEXT already settled. Where CONTEXT explicitly left a value to
"Claude's discretion," this document makes that call and states the reasoning — it does not
leave it open a second time.

## Typeface & Loading Contract (DES-01, DES-02, DES-04)

These are locked decisions restated as an exact build checklist — not open questions:

1. Place the variable WOFF2 at `docs/public/fonts/source-sans-3-variable.woff2` (Latin subset,
   one file, weight axis covering at minimum 400–700).
2. Author in `custom.css` (replacing the current `@import url('https://fonts.googleapis...')`
   at line 7, which must be deleted entirely):
   ```css
   @font-face {
     font-family: 'Source Sans 3';
     src: url('/fonts/source-sans-3-variable.woff2') format('woff2-variations');
     font-weight: 200 900;
     font-style: normal;
     font-display: swap;
   }
   ```
3. Add to `config.js`'s `head` array:
   ```js
   ['link', { rel: 'preload', href: '/fonts/source-sans-3-variable.woff2', as: 'font', type: 'font/woff2', crossorigin: '' }]
   ```
4. Set `--vp-font-family-base: 'Source Sans 3', -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, sans-serif;` in `custom.css`'s `:root`. Delete the bare `html { font-family: 'Inter', ... }` declaration (currently `custom.css:94-99`) — do not keep both; the variable is what VitePress default-theme internals read, the bare selector is not.
5. `config.js:86`'s Workbox `globPatterns` already includes `woff2` — no change needed there, just confirm the new file matches once it exists.
6. Verify zero layout shift: with `preload` + `font-display: swap` + a single subsetted file, the swap window should be imperceptible. If a visible flash is observed in manual QA, that is a regression to fix before sign-off, not an accepted trade-off.
7. Confirm zero remaining third-party font network request (DES-01) — after this change, a network panel trace of any page must show no request to `fonts.googleapis.com` or `fonts.gstatic.com`.

Line height: `1.5` for all body/paragraph text (`--line-height-body`), `1.2` for headings
(`--line-height-heading`) as `:root` tokens, replacing the current mixed literals (`1.7` on
`.vp-doc`, `1.05` on hero name, `1.55` on feature details). Declare both as tokens; `1.7` for
body text is unusually loose for a 16px base and should tighten to `1.5` for a denser,
more "brief" reading rhythm appropriate to a 20-second scan.

**`font-variant-numeric: tabular-nums`** — apply via a single rule targeting every numeric
display surface, rather than per-component:

```css
.hero-metric__value,
.vp-doc table,
.viz-panel .echarts-* /* chart canvas labels are unaffected by CSS — see note below */ {
  font-variant-numeric: tabular-nums;
}
```

Note: ECharts renders numeric labels to canvas, not DOM text — `font-variant-numeric` has no
effect there. For chart-rendered figures, tabular alignment must come from each chart
component's `textStyle`/`label.fontFamily` already resolving to the same variable-font family
(Source Sans 3 does have tabular figure support at default settings); no additional chart-level
change is required beyond the font-face swap itself. The CSS rule above covers `HeroMetrics`
values and any HTML `<table>` (used in Cisco's DCF component table and the Board Diversity
hypothesis table) — this is where `tabular-nums` is structurally meaningful and verifiable.

## Color

The existing brand palette (`--vp-c-brand-1: #0071e3` light / `#2997ff` dark, already
consolidated in Phase 3) is **not** being replaced — this phase fixes where colour is
duplicated or hard-coded outside that system, not the palette itself.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--vp-c-bg` (`#fff` / `#000`) | Page background |
| Secondary (30%) | `--vp-c-bg-alt` / `--vp-c-bg-soft` / `--vp-c-bg-elv` | Cards, `VizPanel` body, footer, nav/sidebar glass |
| Accent (10%) | `--vp-c-brand-1` (`#0071e3` / `#2997ff`) | Reserved for: primary CTA button, active nav/sidebar indicator, in-text links, focus ring, badge/eyebrow text, `VizPanel` top hairline (see restraint fix below), first-position chart series colour |
| Destructive | not applicable | No destructive UI action exists on this site (matches Phase 2's finding) |
| Semantic — negative | `--color-negative` (new token, `#ff3b30` light / kept identical in dark — a warning red does not need a dark-mode shift the way brand does) | Chart/metric values signalling an unfavourable finding (e.g. Cisco's "Market price" overvaluation marker, VaR loss figures) |
| Semantic — positive | `--color-positive` (new token, `#34c759`) | Chart/metric values signalling a favourable finding |

**Accent is not "all interactive elements."** It is reserved for exactly the six uses listed
above. Everything else (body links styled via `.vp-doc a` already correctly use brand — that
one stays) uses text-color tokens, not brand, for anything that isn't foregrounding an action
or a primary data point.

### Brand/RGB literal consolidation (DES-07, carried forward from Phase 3)

`custom.css` still expresses brand-derived translucent values as hand-copied `rgba()` literals
independent of `--vp-c-brand-1`, each needing a separate `.dark` override today:

| Rule | Current | Fix |
|------|---------|-----|
| `--vp-c-brand-soft` (`:root` and `.dark`) | `rgba(0, 113, 227, 0.1)` / `rgba(41, 151, 255, 0.12)` | `color-mix(in srgb, var(--vp-c-brand-1) 10%, transparent)` — one declaration, no `.dark` override needed, matches the pattern `VizPanel.vue` already uses |
| `.vp-doc .custom-block.tip` background (`:root` and `.dark`) | `rgba(0, 113, 227, 0.06)` / `rgba(41, 151, 255, 0.1)` | `color-mix(in srgb, var(--vp-c-brand-1) 6%, transparent)` |
| `::selection` background (`:root` and `.dark`) | `rgba(0, 113, 227, 0.2)` / `rgba(41, 151, 255, 0.3)` | `color-mix(in srgb, var(--vp-c-brand-1) 20%, transparent)` |

This removes six literal occurrences down to three `color-mix()` expressions, each
automatically dark-mode-correct with no `.dark` block entry required — a strict simplification,
not a visual change (percentages chosen to match the current rendered opacity as closely as
`color-mix` permits).

### Chart colour architecture (DES-07, DES-11, EXH-05 — the load-bearing fix)

**The problem:** 23 occurrences of `#0071e3` (plus `#5856d6`, `#af52de`, `#34c759`, `#ff9500`,
and others) are hard-coded directly into `<script setup>` data arrays across all five case-study
markdown files, passed as explicit `color`/`accent` props to `EBar`, `EDonut`, `HeroMetrics`,
etc. Explicit per-item props correctly take precedence over each component's internal
theme-reactive fallback — which is exactly why these do **not** re-theme in dark mode today
(e.g. Cisco's Exhibit 7 "Median" marker stays light-brand against re-themed bars).

**The fix has three cases, in order of preference:**

1. **Sequential/categorical series (the majority — segment mix, geo mix, competency
   breakdowns, WACC bars, most bar/donut items): delete the `color:`/`accent:` key from the
   markdown data item entirely.** Every affected component (`EBar`, `EDonut`, `ECombo`,
   `EForest`, `EGroupBar`, `EHistogram`, `EFootball`) already falls back to
   `t.palette[idx % t.palette.length]` when no explicit colour is given — this fallback is
   already theme-reactive (proven in Phase 3). This is a markdown-only edit, zero component
   code change, and fixes the majority of the 23 occurrences.
   Likewise, `HeroMetrics`' `accent` prop already falls back to `var(--vp-c-brand-1)` — delete
   `accent: '#0071e3'` wherever the intent is just "brand emphasis," not a specific semantic
   colour. `global-equity-portfolio.md`'s metrics array already omits `accent` entirely and is
   the reference example other case studies should match.

2. **Fixed-semantic values that must render an intentional colour regardless of palette
   position** (Cisco's "Market price" overvaluation marker and `EFootball`'s hard-coded
   `#ff3b30` market line; the VaR/CVaR red-amber-green triad): extend `echarts-setup.js`'s
   `themeTokens()` to resolve two new semantic slots exactly like `brand` is resolved —
   ```js
   negative: cssVar('--color-negative', '#ff3b30'),
   positive: cssVar('--color-positive', '#34c759'),
   ```
   backed by `--color-negative` / `--color-positive` custom properties added to `custom.css`
   `:root` (Colour table above). Extend the affected components' item-shape contract to accept
   an optional semantic string key (`'negative' | 'positive'`) alongside the existing
   raw-colour/undefined shape, resolved internally via `t.negative`/`t.positive` — e.g. in
   `EBar.vue`: `i.color === 'negative' ? t.negative : i.color === 'positive' ? t.positive : (i.color || t.palette[idx % t.palette.length])`.
   Markdown then writes `color: 'negative'` instead of `color: '#ff3b30'`. This is the one
   place this phase adds a small, explicit prop-contract extension rather than a pure deletion
   — proportionate because it is exactly two new semantic slots, not a general theming layer.
   `EFootball.vue`'s hard-coded `backgroundColor: '#ff3b30'` / `lineStyle.color: '#ff3b30'` for
   the market marker (lines ~131, 137) become `t.negative` inside the component (this one is a
   direct component fix, not a markdown data change, since the market line isn't driven by the
   `ranges` prop).

3. **CSS-var strings cannot be passed to ECharts item colours** — canvas rendering does not
   resolve `var()`; every colour value ECharts receives must already be a computed literal
   (hex/rgb string), which is why case 2 resolves inside the component's reactive `computed()`,
   not by embedding a `var(--x)` string in markdown data.

**Net result:** the hex literal count in case-study markdown drops from 23+ to zero; every
chart element re-themes correctly on toggle (DES-11); every colour that matters (win/loss,
brand, sequential) is a single named source (DES-07).

## Motion Contract (DES-09)

**Current state:** two permissive `@media (prefers-reduced-motion: no-preference)` gates exist
(`custom.css:154` hero fade-up, `custom.css:437` page-transition fade) — correct as far as they
go, but **no `reduce` block exists anywhere**, so everything *not* wrapped in a `no-preference`
gate keeps animating regardless of the user's OS setting: theme-switch colour transitions
(`custom.css:110-115`), `.VPFeature:hover` scale, `.VPButton` hover/active scale,
`.project-card:hover` lift, and all ten ECharts entrance animations (`animationDuration`
700–900ms across `EBar`, `EDonut`, `ELine`, `ECombo`, `EForest`, `EGroupBar`, `EHistogram`,
`EFootball`, `EScorePath`, `EHeatmap`).

**Fix — add a real `reduce` block to `custom.css`** (do not remove the existing
`no-preference` gates; add this as a new, separate rule):

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

This is a universal override (same `!important` pattern already used in the existing `@media
print` block) and correctly disables the hero fade-up, page-transition fade, `.VPFeature`/
`.VPButton`/`.project-card` hover transforms, and the theme-switch colour transitions — all of
which are plain CSS `animation`/`transition` and are fully covered by a universal rule.

**ECharts entrance animations are canvas-rendered and do not respect CSS media queries** — each
of the ten chart components must gate its own `animationDuration` in JS. Add one shared helper
to `echarts-setup.js`, used identically by all ten components:

```js
export function prefersReducedMotion() {
  return typeof window !== 'undefined' &&
    window.matchMedia('(prefers-reduced-motion: reduce)').matches
}
```

Each component's `option`/`optionFinal` computed property changes its literal
`animationDuration: 700` (or 800/900) to `animationDuration: prefersReducedMotion() ? 0 : 700`
(preserving each component's own existing duration when motion is not reduced). This is a
one-line change per component, applied identically across all ten — do not introduce per-chart
duration variance in the reduced-motion path; it is always `0`.
